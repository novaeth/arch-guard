# enable 语义：自定义规则默认在跑、`all` 的副作用要自述、片段要能文档化

Status: done

## 场景（对应 REQUIREMENTS.md 的 R-163；写不出这一节的需求先不做）

- **宿主用 `enable: [...]` 收窄名单 + `customRules` 追加自己的规则**：项目层 `enable` 是**整体替换**，
  自定义规则不在名单里 → **一条都不跑**，报告也不提它（`skipped` 里只有内置规则，宿主以为"我的规则在跑"）。
  真实反馈："我写了三条自定义规则，门禁一直绿，删掉第 3 条也没人发现。"
- **为了省事写 `enable: 'all'`**：它把预设没给的规则也打开（包括能力没配、只能空转的），
  副作用只有一句文档，报告不点名 —— "我全都要"变成了"我不知道我要了什么"。
- **只想补两三条规则**：文档只说"加进 `enable`"，而项目层写 `enable` 会**整体替换**预设清单 ——
  照做就把预设的几十条全丢了，门禁突然全绿。

## 背景与问题

`enable` 的合并语义（预设之间并集、项目层整体替换、`all` 吸收一切）本身是对的，但**三个缺**：
自定义规则不默认参与（被名单静默放下）；`all` 的扩张不可见；"补几条"的正确写法（预设片段）没写进文档。
三者都会把"我以为在跑"变成"其实没跑" —— 与 `not-enabled` 自述要解决的同一类假绿。

## 目标

- **自定义规则默认在跑**：项目层 `enable` 为数组时，自动并入 `customRules` 的 id（显式 `disable` 仍可关）。
- **`enable: 'all'` 的副作用自述**：预设清单不是 `all` 时，新增 notice `enable-all-expanded`，
  点名"额外打开了哪几条"（能力没配的规则会空转）。
- **预设片段文档化**：USAGE 写明"只补几条"的写法 —— 在 `presets` 里放片段 `{ enable: ['S16'] }`
  （预设之间是并集），不要动项目层 `enable`（整体替换）。
- 契约按规矩走：新增 `notices[].code` → `REPORT_API_VERSION` 2→3 + §6.9 版本史 + CHANGELOG 破坏性标注。

## 非目标

- 不改变合并语义本身（预设并集 / 项目层替换 / `disable` 减法）：只把副作用说出来。
- 不做"自定义规则也需要夹具"的告警（框架层无从判断；宿主自己的 CI 负责）。
- 不把 `all` 变成默认值（缺省仍是 `all`，但显式写才自述差异 —— 缺省时用户本来就没收窄）。

## 验收标准

- `customRules` + `enable: ['S01']` → 自定义规则仍在注册/启用集里，不出现 `not-enabled`。
- `enable: 'all'`（预设是清单）→ JSON 有 `enable-all-expanded`，文案含"额外打开了 N 条"；
  `enable: ['S01']` → 没有这条自述。
- `apiVersion === 3`；`NOTICE_CODES` 冻结清单含 `enable-all-expanded`（`tests/report-contract`）。
- 单测 `tests/adoption.test.mjs`；`pnpm check` 全绿。

## 边界与取舍

- **缺省不报**：不写 `enable` = `all`，用户没有"收窄"的意图，报它只是噪音；显式 `all` 与预设清单的差
  才是"用户主动扩权"的审计点。
- **自定义规则"默认在跑"不是"绕过 disable"**：显式 `disable: ['S99']` 仍然关掉它（可见、可审计）。
- 被否方案：把项目层 `enable` 改成"并集"。否掉的理由：整体替换是宿主**收窄门禁**的唯一手段，
  改成并集会让人永远关不掉预设规则 —— 语义没错，缺的是文档与自述。
