# S16 体积阈值按代码行判

Status: done

## 场景（对应 REQUIREMENTS.md 的 R-164）

- 给公开类型补一段 JSDoc 时：`src/engine/types.ts` 这类契约文件本来就有大量"为什么存在"的说明，
  行数一越 500 就被 S16 报红 → 唯一解法是删注释或把类型硬拆到别的文件。**现在：按原始行数报，
  空行与整行注释和代码一样吃预算。**
- 代码 review 要求"复杂逻辑必须写清理由"时：写得越清楚越容易触发体积红线，红线在惩罚写文档。
  **现在：没有区分"代码复杂度"与"注释厚度"。**

## 背景与问题

`Facts.lineCount` 是 `text.split('\n').length`（原始行数），S16 直接拿它比阈值。于是"文件有多长"
把注释与空行当成与代码同等的认知负担 —— 而对引擎 / 库代码来说，注释恰恰是降低理解成本的部分。

## 目标

- S16 的 `fileLines` / `viewLines` 改量**代码行**：空行与整行注释不计，行尾注释所在行照算。
- 默认值不变（500 / 500）；不放宽数字，只修正度量口径。
- 报告文案与 `--render-docs` 的阈值表标签写明「代码行」。

## 非目标

- 不提供 `skipComments` 之类的开关键（口径统一，避免"两个宿主两套长度观"）。
- 不改 `appliesTo: 'product'`（测试脚手架照旧不判）。
- 不做"注释超过 N 行也报"的互补规则（没有真实场景）。

## 验收标准

- `__fixtures__/rules` 新增注释密集的合规文件：原始行超夹具阈值（40），代码行不超 → 不报 S16。
- 同一夹具的 `big.ts`（代码行 45 > 40）仍报，文案含「文件代码」。
- `FACTS_CACHE_SPEC` 11 → 12（事实形状变了，旧缓存必须失效）。
- `pnpm check` 全绿（含夹具回归、文档同步、狗粮）。

## 边界与取舍

- 注释块本身也可能臃肿；宿主若想连注释一起管，可继续用 eslint 的 `max-lines`（默认含注释）作双重保险。
- 「整行注释」按行判：`/* x */ const a = 1` 与 `const a = 1 // x` 都算代码行（该行有代码）。
- 多行块注释内部的空行同样不计。

## Comments

- 2026-11-15 用户问「默认的文件行数限制是不是给太少了」→ 结论：500 不窄，痛点在**度量口径**
  （原始行把注释算进去）；用户拍板「你定」→ 采用"量代码行"，不动默认数字。
